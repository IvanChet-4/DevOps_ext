# «Репликация и масштабирование. Часть 2»

### Задание 1

Опишите основные преимущества использования масштабирования методами:

- активный master-сервер и пассивный репликационный slave-сервер; 
- master-сервер и несколько slave-серверов;


*Дайте ответ в свободной форме.*

#### Решение  

1. Активный master-сервер и пассивный репликационный slave-сервер:  

Эта конфигурация (часто называемая Master-Standby или классическим Failover-кластером) ориентирована не на распределение текущей нагрузки, а на отказоустойчивость, надежность и безопасность. Пассивный слейв не принимает запросы от пользователей, а лишь зеркалирует мастер. (В случае отказа мастер ноды, слэйв становится мастером до момента включения/возвращения мастер ноды)   

Основные преимущества:  
--Отказоустойчивость (High Availability) и быстрое восстановление  
--Безопасное создание бэкапов без потери производительности  
--Минимальные риски повреждения данных  
--Простота обслуживания  

2. Master-сервер и несколько slave-серверов:  

Эта схема (классический Read-Scaling) создана для горизонтального масштабирования производительности высоконагруженных систем, где количество чтений данных значительно превышает количество записей (например, интернет-магазины, соцсети, новостные порталы). Все операции записи (добавление, изменение, удаление) идут на master, а все операции чтения (просмотр каталога, поиск, генерация отчетов) распределяются между слейвами.  

Основные преимущества:  
--Колоссальное увеличение производительности на чтение (за счет распределения нагрузки)  
--Эффективная аналитика и Big Data  
--Гибкое и дешевое масштабирование  
--Повышенная живучесть системы на чтение

### Задание 2


Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц: 

- пользователи, 
- книги, 
- магазины (столбцы произвольно). 

Опишите принципы построения системы и их разграничение или разбивку между базами данных.

*Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера.* 

#### Решение

Data Dictionary:  
  
Таблица users (Пользователи)  
Эта таблица содержит персональные данные клиентов. Из-за потенциально огромного количества пользователей она подвергается горизонтальному шардингу.  
  
|Имя колонки|Тип данных|Ограничения|Описание и роль в архитектуре|
|:---:|:---:|:---|:---|
|user_id|BIGINT|PRIMARY KEY, AUTO_INCREMENT|Уникальный идентификатор пользователя. Используется как Shard Key (ключ шардирования) для распределения строк по серверам.|
|first_name|VARCHAR(50)|NOT NULL|Имя пользователя.|
|last_name|VARCHAR(50)|NOT NULL|Фамилия пользователя.|
|email|VARCHAR(100)|NOT NULL, UNIQUE|Электронная почта. Используется для авторизации. Должна быть уникальной в рамках всей системы (проверка уникальности переносится на уровень приложения).|
|registration_date|TIMESTAMP|NOT NULL, DEFAULT NOW()|Дата и время регистрации аккаунта. Может использоваться для временного (Range-based) шардирования.|


Таблица books (Книги)  
Таблица представляет собой каталог товаров. Из-за большого ассортимента и частых поисковых запросов она разделена вертикально от пользователей и шардируется горизонтально.  

|Имя колонки|Тип данных|Ограничения|Описание и роль в архитектуре|
|:---:|:---:|:---|:---|
|book_id|BIGINT|PRIMARY KEY, AUTO_INCREMENT|Уникальный идентификатор книги. Используется как Shard Key для хэш-шардирования каталога.|
|title|VARCHAR(255)|NOT NULL|Название книги.|
|author|VARCHAR(150)|NOT NULL|Автор или соавторы произведения.|
|isbn|VARCHAR(13)|UNIQUE|Международный стандартный книжный номер (13 цифр). Позволяет однозначно идентифицировать издание.|
|price|DECIMAL(10,2)|NOT NULL, CHECK (price >= 0)|Стоимость книги. Тип DECIMAL исключает ошибки округления, свойственные числам с плавающей точкой.|
|stock_quantity|INT|NOT NULL, DEFAULT 0|Текущий остаток книги на складах/в магазинах. Самая часто обновляемая колонка (UPDATE).|  
  
Таблица stores (Магазины)  
Таблица содержит информацию о физических точках продаж. Поскольку количество магазинов ограничено, таблица компактна, не требует горизонтального шардинга и изолирована на отдельном вертикальном сервере.  

|Имя колонки|Тип данных|Ограничения|Описание и роль в архитектуре|
|:---:|:---:|:---|:---|
|store_id|INT|PRIMARY KEY, AUTO_INCREMENT|Уникальный идентификатор филиала магазина. Достаточно типа INT, так как магазинов не бывают миллиарды.|
|store_name|VARCHAR(100)|NOT NULL|Название или номер филиала (например, «Буквоед №5»).|
|city|VARCHAR(50)|NOT NULL|Город, в котором расположен магазин. Используется для региональной фильтрации на бэкенде.|
|address|VARCHAR(255)|NOT NULL|Полный физический адрес (улица, дом, строение).|
|manager_name|VARCHAR(100)|NOT NULL|ФИО управляющего данным магазином для административной связи.|  
  
В реальных распределенных системах транзакционные таблицы (заказы, платежи, логи) растут быстрее всего и требуют самого детального проектирования. Схема должна состоять из 4 уровней:  
--Слой приложения (Бэкенд): Отправляет запросы.  
--Слой маршрутизации (Шардинг-прослойка / Router): Например, ProxySQL, Spider для MySQL или Citus/PgBouncer для PostgreSQL. Он решает, куда слать запрос.  
--Слой вертикального разделения (Кластеры): Разделение на 3 независимые физические группы (Кластер Users, Кластер Books, Кластер Stores).  
--Слой горизонтального шардинга и репликации: Внутри каждого кластера.

 Режимы работы серверов:  
Каждый узел в инфраструктуре работает в строго определенном режиме для балансировки нагрузки и обеспечения высокой доступности (High Availability):  
--Маршрутизатор (Router):  
Работает в режиме Stateless (без сохранения состояния). Он парсит SQL-запрос от бэкенда, извлекает значение ключа шардирования (user_id или book_id) и перенаправляет запрос на нужную физическую ноду.  
--Кластер Users (Шардирован + Репликация):  
Шард 1 (User_id % 2 = 0): 1 Сервер Master (режим Read-Write для записи: INSERT, UPDATE, DELETE) + 1 Сервер Slave (режим Read-Only с асинхронной репликацией для чтения: SELECT).Шард 2 (User_id % 2 = 1): 1 Сервер Master (Read-Write) + 1 Сервер Slave (Read-Only).  
--Кластер Books (Шардирован + Репликация):  
Шард 1 (Book_id % 2 = 0): 1 Сервер Master (Read-Write) + 1 Сервер Slave (Read-Only).Шард 2 (Book_id % 2 = 1): 1 Сервер Master (Read-Write) + 1 Сервер Slave (Read-Only).  
--Кластер Stores (НЕ шардирован, только отказоустойчивость):  
Нода Stores Master: Работает в активном режиме Read-Write, принимая как запросы на запись, так и на чтение, поскольку объем данных невелик.Нода Stores Standby: Находится в режиме Hot-Standby (пассивный слейв для горячего резерва). Он непрерывно синхронизируется с мастером таблицы stores, не принимает пользовательский трафик, но при падении мастера автоматически переключается в режим Master (процесс Failover).  
  
Связи JOIN запрещены на уровне СУБД. Склеивание данных выполняется на уровне приложения (Application-level joins)

Принципы разграничения и разбивки данных:  
--Вертикальный разрез:  
Данные разделены по функциональному признаку. База данных Stores полностью изолирована от Users и Books. Прямые связи FOREIGN KEY между таблицами на разных серверах отсутствуют. Проверка целостности данных ложится на бизнес-логику кода.  
--Горизонтальный разрез:  
Для Users и Books применяется Hash-based шардинг по формуле ID % 2. Это позволяет равномерно распределить данные по двум серверам-шардам и избежать проблемы «горячих точек» (когда один сервер перегружен, а второй простаивает).

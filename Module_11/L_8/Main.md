# «Резервное копирование баз данных»

### Задание 1. Резервное копирование

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

#### Решение

 Для реализации сценария 1.1 подходит классическая схема ежедневного полного резервного копирования (Full Backup).  
Как это работает:  
Каждый день (обычно в ночное время, когда нагрузка на систему минимальна) создается полная копия всей базы данных.  
Применение в кейсе:  
Если поломка происходит в любой момент текущего дня, система откатывается к состоянию на момент завершения ночного бэкапа. Данные, накопленные за текущий день, будут потеряны, но требование «восстановить за предыдущий день» будет выполнено.  
Плюсы:  
Максимально простая и надежная схема восстановления; для поднятия базы нужен всего один файл бэкапа.

Для реализации сценария 1.2 необходимо использовать инкрементальное резервное копирование (Incremental Backup) или бэкап журналов транзакций (Transaction Log Backup).  
Как это работает:  
Раз в сутки (например, ночью) делается Full Backup.Каждый час запускается копирование только тех изменений, которые произошли с момента предыдущего бэкапа (инкремент или журнал транзакций).  
Применение в кейсе:  
Если авария произошла в 14:45, базу данных восстанавливают из ночного полного бэкапа, а затем поочередно накатывают часовые бэкапы журналов вплоть до копии, сделанной в 14:00. Потеря данных составит максимум 45 минут, что полностью укладывается в рамки «за час до поломки».  
Плюсы:  
Экономия дискового пространства и высокая точность восстановления (низкий RPO).  

Сценарий 1.3 относится уже не к классическому резервному копированию, а к обеспечению высокой доступности (High Availability, HA) и отказоустойчивости.  
Для моментального (или почти моментального — в пределах нескольких секунд) переключения используются следующие технологии:  
Репликация (Replication):  
Данные из основной БД (Master/Primary) непрерывно и в реальном времени копируются на резервную БД (Slave/Replica). Репликация должна быть синхронной, чтобы на резервной базе гарантированно были абсолютно все актуальные финансовые транзакции.  
Кластеризация и Failover:   
Базы данных объединяются в кластер под управлением специального ПО (балансировщика или кластерного менеджера). При выходе из строя основной базы, система автоматически перенаправляет трафик клиентов на резервную (этот процесс называется Failover).  
Примеры решений:  
PostgreSQL (Patroni + Streaming Replication), MySQL (InnoDB Cluster), MS SQL Server (Always On Availability Groups).

### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*

#### Решение

2.1 Примеры команд резервирования и восстановления для утилит pg_dump и pg_restore на основе официальной документации PostgreSQL:  
Для обеспечения гибкости и надежности в PostgreSQL принято использовать сжатый формат бэкапа (-F c), который позволяет восстанавливать базу многопоточно и выбирать отдельные объекты. Создание резервной копии (pg_dump)  

Команда для резервирования конкретной базы данных:  

```
pg_dump -U username -h localhost -p 5432 -F c -b -v -f /path/to/backup/my_db_backup.dump my_database
```


Команда для восстановления из созданного ранее дампа:

```
pg_restore -U username -h localhost -p 5432 -d my_database -v /path/to/backup/my_db_backup.dump
```

2.1* Возможно ли автоматизировать этот процесс? - Да.

Сначала настраивается авторизация без ручного ввода пароля:

Утилиты pg_dump по умолчанию запрашивают пароль. Чтобы автоматизировать процесс, используют файл .pgpass в домашней директории пользователя, из-под которого запускается скрипт (например, /home/user/.pgpass). В файл записывается строка в формате:

```
localhost:5432:my_database:username:password
```

Далее создается скрипт с командами для автоматического бэкапа:

В зависимости от операционной системы используются разные инструменты автоматического вызова:В Linux (cron):Самый частый способ. Создается bash-скрипт (например, backup.sh), внутри которого прописана команда pg_dump с динамическим добавлением даты в имя файла:

```
#!/bin/bash
BACKUP_DIR="/path/to/backup"
DATA_REC=$(date +%Y-%m-%d_%H-%M-%S)
pg_dump -U username -h localhost -F c -f "$BACKUP_DIR/db_$DATA_REC.dump" my_database
```
(файлу со скриптом присваивают необходимые права)

Далее скрипт добавляется в планировщик задач:

Например в crontab -e. Запись для ежедневного запуска в 02:00 ночи выглядит так:

```
0 2 * * * /bin/bash /path/to/scripts/backup.sh
```
